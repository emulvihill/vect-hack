# be3.7 — Pointer targets beyond monsters and doors; command reachability without letters

Bead: `vect-hack-be3.7`, under epic `vect-hack-be3` (modern control scheme).
Date: 2026-07-29.

## Why

be3.3–be3.6 shipped the pointer action layer, the pointer-driven inventory,
loadable keybindings and gaze-relative direction prompts. The epic's acceptance
— "game fully playable without memorizing classic keybindings" — is still
unmet: `MENU_TABLE` has two rows (monster, door), and every no-target command
(inventory, pick up, search, stairs, save) needs its letter.

## What the bead got wrong, and the correction

The bead lists "items, stairs, fountains, altars, floor" as missing *pointer*
targets. They can't be pointer targets:

- Those verbs are all **stand-on** verbs in NetHack. You cannot pick up an item
  in an adjacent cell, or quaff from a fountain you are standing next to.
  Reaching them by pointer would mean walking there first — click-to-move,
  which be3.2 declined outright.
- The hero's own cell renders as `@`. `MapModel` stores one glyph per cell, so
  the terrain and objects underneath the hero are not visible to it at all; a
  hero-cell menu could not know whether there are stairs below.

So the stand-on and no-target verbs belong in a **global command menu**, and
what is genuinely left for the map is a short list of adjacent-only verbs.

## Design

### 1. Command menu — a persistent `☰` button

A button in `#stage` (top-left; the radar owns top-right) opens a two-level
menu of everyday commands.

New module `src/ui/hud/commandMenu.ts`, pure data:

```ts
export interface Command { label: string; code: number }
export interface CommandGroup { label: string; commands: readonly Command[] }
export const COMMAND_GROUPS: readonly CommandGroup[]
```

| Group | Rows |
|---|---|
| Items | Inventory `i`, Pick up `,`, Drop `d`, Eat `e`, Read `r`, Quaff `q`, Apply `a` |
| Gear | Wield `w`, Wear `W`, Take off `T`, Put on `P`, Remove `R`, Throw `t`, Fire `f` |
| Explore | Search `s`, Rest a turn `.`, Look here `:`, Go up `<`, Go down `>` |
| Magic | Cast a spell `Z`, Zap a wand `z`, Engrave `E`, Pray `M-p` |
| Game | Discoveries `\`, Dungeon overview `^o`, Options `O`, Help `?`, Save and quit `S` |

Every letter is verified against `external/NetHack/src/cmd.c`'s command list at
the pinned revision, not from memory. `pray` is `M('p')` and `untrap` is
`M('u')` — plain compiled-in keys, exactly like chat's `M('c')` — so nothing
here needs NetHack's extended-command (`#`) machinery, which our `extCmd()`
answers with a DOM `<input>` that a synthetic keystroke could not reach anyway.

Directional verbs (open, close, kick, untrap, force-fight) are deliberately
**absent** from this menu: they need a target, and the map is where a target is
chosen.

These rows stay `{label, code}` and do **not** become `Action` names in
`moveKeys.ts`. An `Action` exists so one verb resolves identically from a key,
a click or a menu row *against a direction*; these have no direction and no
rebinding story, so adding 28 of them would bloat `ACTIONS` and the
be3.5 binding table for no gain.

**Ownership.** `TextHud` owns the button, because `TextHud` owns all text
chrome and is shared by both views — the debug view gets the menu for free.
It reuses the existing `showActionMenu(rows)`: a category row's `run()` calls
`showActionMenu` again with that group's rows plus a `‹ Back` row. No new menu
mechanism, no submenu positioning problem.

**Bug this surfaces.** `showActionMenu`'s `onRowClick` currently runs
`rows[i].run()` and *then* `close()`. If `run()` opens a submenu, the outgoing
closure's `close()` then sets `this.actionMenu = null`, so the new menu is on
screen but untracked: Escape stops closing it, and `showOverlay`/`runMenu` stop
tearing it down when they claim `#overlay`. Fix: close first, then run.

**Discoverability.** The button carries a `title` and stays visible at all
times; that is the whole affordance. It uses `tabindex="-1"` and blurs itself
after a click, so it can never swallow a Space or Enter meant for the game.

### 2. Cell targets

New and changed `MENU_TABLE` rows in `pointerActions.ts` — all adjacency-gated:

| Target | Actions |
|---|---|
| monster (non-pet) | Attack, Chat, Kick |
| monster (pet) | Chat |
| closed door `+` | Open, Kick, Apply |
| open door (brown `-`/`\|`) | **Close**, Kick, Apply |
| wall | **Search** |
| trap | **Untrap** |
| object, feature | **Kick** |
| floor, corridor, stairs, water, lava | nothing |

Kick reaches boxes, sinks, thrones and monsters — the classic "kick it and see".
It stays off floor, corridor and wall, where it only wastes a turn or a leg.

One `PRIMARY_TABLE` row, the one be3.3's design explicitly reserved: closed door
→ left-click opens it. This intentionally flips the existing test
`"has no primary action for a target with no obvious verb yet (a door)"`.

`moveKeys.ts` gains `close`, `search` and `untrap` in `ACTIONS` and
`resolveTarget`:

- `close` → `[key("c"), direction]`
- `untrap` → `[meta("u"), direction]`
- `search` → `key("s")`, no direction (like `apply`); the row's adjacency gate
  is what makes offering it on a wall meaningful.

`meta("u")` is ≥ 128, and safe for the same reason `meta("c")` already is: the
verb byte is read by the command loop (`rhack`), never by a `yn_function`
return converter, and only ASCII direction letters follow it in the queue.

### 3. The review note about `dir === null`

The bead carries a be3 review finding: "`applicableActions`' `dir===null` early
return hard-codes adjacency-relative verbs — move that gate into the rows when
adding non-directional targets."

**Resolution: keep the early return**, and document why. Every row above is
adjacency-relative, and the non-directional verbs that motivated the note now
live in the command menu instead, where there is no target and so no gate.
Moving the gate would duplicate `dir !== null` into eight rows for no change in
behaviour. The comment records the condition under which the note becomes live
again: the first `MENU_TABLE` row whose verb does not need a neighbour.

### 4. Clickable `yn_function` choices

Today `#prompt` is plain text and `ynFunction` only reads keys, so half the
command menu's rows dead-end on a typed `y` ("Really save? [yn]", "Drink from
the fountain? [ynq]").

`ynFunction` renders each character of `choices` as a `.ynchip` element, plus a
trailing `esc` chip that feeds `ESC`. A single delegated listener installed once
on `#prompt` reads `data-yn` and calls `feedKey`. Chips only exist while a
choices-bearing prompt is up, since the `finally` clause already blanks
`#prompt`.

Empty-`choices` prompts render no chips. That includes `getdir()`, so be3.6's
arrow-answers-a-direction-prompt path is untouched.

## Testing

- `scripts/test/pointer-actions.test.ts` — extend: close/kick/apply on an open
  door, search on a wall, untrap on a trap, kick on an object and a feature,
  kick added to the monster rows, nothing on floor/corridor/water, open as the
  primary action on a closed door, and label coverage for every `MenuAction`.
- `scripts/test/command-menu.test.ts` (new) — every code is a printable command
  byte or a documented `ctrl`/`meta` fold, labels are unique across all groups,
  no group is empty or longer than eight rows, and no code collides with a
  directional verb the cell menus own.
- `scripts/test/move-keys.test.ts` — `resolveTarget` cases for `close`,
  `search`, `untrap`, including the `dir === null` refusals for the two
  directional ones.
- `npm run typecheck` and `npm test` gate the change; a browser playtest of the
  whole be3 surface is already filed separately as `vect-hack-be3.8`.

## Out of scope

- Click-to-move / travel (declined, be3.2).
- A keybinding editor UI (declined, be3.5).
- Farlook (`;`) from a click: it drives `getpos()`, which needs cursor movement
  keys rather than a single keystroke.
- Grouping or filtering in the inventory (declined during the be3 scope pass).
